# Research progress API

All routes use `/api` and the existing validation/error envelope. Roadmap, goals and achievements award no XP.

- `GET /roadmap`, `GET /roadmap/:levelNumber`: independent Preparation Camp (level 0, year null) plus twelve research chapters (1-12) across three years.
- `PATCH /roadmap/:levelNumber`: `{ "title"?: "...", "description"?: "..." }`: supply at least one field; title is nonblank up to 160 characters, description nonblank up to 3000. Initial guidance is provisional and editable.
- `PATCH /roadmap/:levelNumber/checkpoints/:checkpointId`: `{ "completed": true|false, "evidence"?: "..." }` (evidence up to 2000 characters). Only the current chapter accepts validation or correction, starting with Preparation Camp. First validation history is retained.
- `POST /roadmap/:levelNumber/complete`: `{ "confirm": true }`. Requires every mandatory checkpoint. For levels 1-11, completion and unlocking the next chapter are one transaction. Level 0 completion unlocks the next unfinished research chapter, preserving any earlier completed work. Repeats are idempotent; chapter 12 creates no further chapter. Completed checkpoints cannot be reversed. Metadata edits preserve progress.
- Initialization inserts Preparation Camp and twelve research chapters atomically into an empty map. Existing complete twelve-chapter maps gain only the missing camp, without renumbering or erasing research work. While camp is incomplete, later current chapters are locked until camp completion. Existing descriptions and progress are preserved; a partial map requires explicit repair.

- `GET /goals?type=weekly|monthly|research&status=active|completed|archived`: filters are optional.
- `POST /goals`, `PATCH /goals/:id`: title (nonblank, max 160), description (max 2000), type; optional targetDate, relatedWeekId, relatedRoadmapLevel. Dates use real `YYYY-MM-DD` calendar dates. Week references require an existing Sunday-start plan; chapter references require an existing level. Optional links/due date may be cleared with null.
- `PATCH /goals/:id/complete`, `/reopen`, `/archive`: empty JSON body. Completion/reopening is idempotent and preserves first-completion history. Archive is terminal: retained for filtering, with no editing or reopening. Goals can be independent of other records and never complete tasks/checkpoints.

- `GET /achievements`: reconciles eight definitions against authoritative persisted evidence in a transaction. Dashboard reads also reconcile. Unlock timestamps are written only once. Distinct historical task source IDs count toward ten tasks; longest streak, first checkpoint validation and first goal completion survive subsequent corrections or reopening. Unlock dates indicate when reconciliation recognized the milestone.
- `GET /dashboard`: one snapshot of gamification, current Sunday?Saturday week in APP_TIMEZONE, today's tasks, scheduled/recorded workload, current research chapter and separate Preparation Camp state, five recent active goals plus total, ten recent completion events, and achievement totals/recent unlocks. Missing current plan returns planId/progress null. Weekly baseline is 360 minutes. Uses existing XP, streak and weekly-progress calculations.

Focused checks: after `npm run build`, `node --test test/research/dashboard.test.cjs`; Mongo-backed checks `node test/research/{roadmap,goals,achievements}.check.cjs` each create/drop only their own random validation database using MONGODB_URI. `api.check.cjs` requires a separately started, disposable API and explicit RESEARCH_TEST_BASE_URL / RESEARCH_TEST_DB_URI; it leaves fixtures for browser checks. Never point that API at user data. No reset/reseed endpoint is provided.

## Optional connected progress

Goals accept `linkedTaskIds` on create/edit: up to 200 unique existing `weekId:taskId` strings. Omit the field to preserve links; send `[]` to remove them. Goals without links remain manual (`progress.mode: manual`, percentage null). Linked responses include task titles/states and completed/total/percentage. Read snapshots batch task lookup across weeks. Reopening tasks reduces derived progress without undoing manually confirmed goal completion; linked goals never grant extra XP.

`PATCH /roadmap/:levelNumber/checkpoints/:checkpointId/goals` accepts `{goalIds:[...]}` (up to 100 unique existing goal IDs; `[]` clears). Only the current chapter can edit checkpoint links. Completed and locked chapters remain read-only. Roadmap responses include compact linked-goal summaries and derived checkpoint progress separately from manual checkpoint validation. A goal may contribute to several checkpoints. Standalone completed goals contribute 100%, active ones 0%; archived standalone goals retain the completion state represented by completedAt. Task-linked goals always contribute their current task fraction, even if completed/archived. Equal weights apply, with Math.round to whole percentages; checkpoint means use exact task fractions and round only the final result. Reaching 100% completes/validates/unlocks nothing automatically.

Relationships are optional embedded arrays, not a new collection. All edits share the application-wide transactional guard. Roadmap import clears checkpoint goal links along with the replaced checkpoints while retaining goals and their task links. Existing relatedRoadmapLevel values remain chapter references, not links to replaced checkpoints. Version-1 backups retain optional goals.linkedTaskIds and checkpoint.goalIds; older files may omit them. Restore rejects missing or duplicate references. Derived progress is never persisted or included as backup state.
