# Task progress contract

- PATCH `/api/weekly-plans/:planId/tasks/:taskId/complete` accepts `{actualMinutes?: integer 0..1440}`. Task IDs are the imported stable IDs, scoped to a saved plan. Already completed is HTTP 200 with changed=false; supplied minutes are ignored on no-op requests.
- PATCH `/api/weekly-plans/:planId/tasks/:taskId/reopen` accepts an empty object or no body. Already pending is a no-op. Reopen clears current completedAt but retains actual minutes and firstCompletedAt. A real recompletion may replace actual minutes; omission preserves the last recorded value.
- Both return `{changed, xpAwarded, plan, weeklyProgress, gamification}` from one transactional snapshot. No optimistic XP is required. GET `/api/weekly-plans/:planId/progress` and GET `/api/gamification/summary` provide snapshot-consistent readback.

Invariants: identity is weekId:taskId; task state, reward and activity commit together or roll back together. A unique (sourceType,sourceId) index protects immutable task_completion XP records. Only first completion may award XP. Reopen never reverses it; recompletion never pays again. Zero-XP tasks create no ledger entry but retain a first-completion marker and immutable activity event. Existing completed tasks are not retroactively rewarded or backfilled; reopening retains their old completion timestamp as a first-completion marker. All-task completion counts include optional tasks; empty weeks have zero progress, not 100%. Actual recorded workload includes retained minutes on reopened tasks; weekly earned XP includes retained ledger rewards.

The ledger is the only source of total earned XP. Player level L starts at threshold `25 * (L - 1) * (L + 2)` XP: 0,100,250,450,700,1000,1350,... . Player level is independent of the research roadmap. Summary totalCompletedTasks counts currently completed tasks, not historical transitions.

APP_TIMEZONE defaults to Africa/Casablanca and is validated at startup. Server completion instants are converted using Intl with that explicit timezone; scheduled task dates do not affect activity. Each real pending-to-completed transition appends one immutable event to daily_activity and increments that date's count. Repeated completion does not. Reopen erases neither events nor rewards. Current streak ends today or yesterday; otherwise it is zero. Longest streak is derived from historical consecutive calendar dates. Daily activity has a unique date index. There are no client-supplied timestamps or timezone overrides per request.

Timezone offsets follow Node's IANA data, including historical changes; never assume a fixed +1 offset. Changing APP_TIMEZONE after activity exists requires a deliberate migration policy; stored dates are not automatically relabeled. Summary reads and progress responses are snapshot-consistent. The UI refreshes on loading a plan and confirmed mutations; it does not push updates across tabs.

MongoDB transactions use snapshot reads and majority writes. Driver transaction retries handle transient/uncertain commits; a bounded retry handles expected ledger/date unique-key races after abort. Unexpected failures propagate. No task completion, XP or activity is written by import. No roadmap/goal/achievement logic is included.

Focused checks: `npm run test:progress` for deterministic rules/DTOs; `npm run test:progress:transactions` with MONGODB_URI for a live transaction check that creates and drops only its own UUID database. The API check requires PROGRESS_TEST_BASE_URL on a separate validation backend and PROGRESS_TEST_DB_URI pointing to its owned phd_quest_phase5_validation_UUID namespace; that backend/database lifecycle and cleanup must be managed by the caller. Never aim it at the real backend. Existing tests remain available; no full unrelated suites or new test framework are required.
